# 连续开发、自检、修复与Git推送工作流
这是后续执行软件必须遵守的执行协议。用户已授权按模块连续开发、自检、修复、提交和推送GitHub，无需每模块询问。它不能覆盖执行环境本身的权限限制；真实外部阻塞如实记录。

## 1. 启动与分支
1. 读取01开发方案、当前仓库AGENTS.md/CLAUDE.md等适用规则、package.json、CI配置和Git状态。
2. 检查origin是否指向CHEN-Cowen/qiantubailian-commerce。核对当前分支、upstream、未提交文件与最近提交。保留用户原有改动，不替用户提交无关文件。
3. 获取远端更新，确认当前分支与远端关系。优先采用已为本任务指定的开发分支；没有指定则创建product-rebuild-20261107，冲突时加短后缀，并设置upstream。默认把全部模块推送到这一远端开发分支，不自动合并主分支。
4. 检查CI/CD是否会因开发分支push自动部署、发布或产生额外费用。普通测试CI可正常触发；生产部署只使用既有明确授权，否则采用不触发生产部署的开发分支。用户要求推送远端不等同直接改生产服务器。
5. GitHub认证只使用已有安全凭据，不输出密钥，不把token写入仓库。缺凭据时继续可完成的本地开发和测试，记录待推送提交；认证恢复后按原顺序补推并验证。不要把push失败当完成。
6. 将交接包放到docs/product-rebuild/，初始化进度和功能矩阵。禁止直接覆盖已有同名记录，应合并并保留历史。

## 2. 每模块自动循环
依次执行M00至M08，直到全部完成或出现真实外部阻塞：
A. 从PROGRESS读取当前模块；读取该模块详细要求与相关现有代码，列出本模块需求ID和将修改的路径。
B. 实现完整业务行为，更新功能矩阵。模块完成后再开展后续模块，避免多个半完成流程混在一起。
C. 执行check、受影响行为测试、必要浏览器检查。涉及费用、权限、数据兼容、任务状态时必须覆盖相应失败分支。按01约定节点运行全套测试。
D. 发现失败：定位原因→修复→重跑失败项与受影响回归。遇到同一失败连续三次时改变诊断方法并记录证据，不能只重复命令。不能通过跳过测试、移除功能、放宽安全限制或伪造数据取得绿色。
E. 通过后写reports/Mxx.md和PROGRESS。模块状态先设verified_local，记录检查命令、结果和证据路径。
F. 查看git diff、diff --check、git status。逐项暂存本模块明确文件，排除.env、数据库、运行时数据、密钥、无关用户文件和大体积生成素材。按本地规范提交，例如feat(rebuild): M04 simplify product information confirmation。
G. 推送本次开发分支。push成功后执行git rev-parse HEAD与git ls-remote --heads origin <branch>，核对远端分支SHA与本地HEAD一致。记录提交SHA并把模块标为pushed。进度文件不要求记录包含自身的提交SHA；可在下一提交或最终汇总补记，避免自引用循环。
H. 若有GitHub自动检查，观察到完成；失败则修复并追加提交推送。无权限查看CI时报告可见范围，不假报CI通过。
I. 自动进入下一模块，发送简短进度而不是权限问题。常规布局、命名、兼容实现、测试修复、提交推送无需再问用户。

## 3. 失败与远端变动
- 自己引入的问题：修复到通过后再标模块完成；失败期间的恢复点可以保存在本地，不把未验证提交推送当模块交付。
- 既有失败：基线记录复现命令与证据。影响当前核心路径则纳入修复；无关且暂不能修复的标明，不宣称全量通过。最终存在必需失败不能结束为成功。
- push网络失败：核对网络/认证/远端后有限重试，保护本地提交；独立开发继续。恢复后补推。待推送状态不能标pushed。
- non-fast-forward：先fetch并检查双方提交。仅在自己的独立开发分支正常合并或按仓库规范rebase；解决冲突后重新测试。保留远端他人更改，禁止force push、reset --hard、clean -fd等破坏性捷径。
- 分支保护：推送开发分支；需要主分支合并时形成可审阅PR或交付分支，不绕过保护。PR创建仅在工具权限和任务规则允许时执行，不以未合并冒充上线。
- 环境缺依赖：按锁文件和仓库规则修复；缺API凭据/额度/服务权限则记录具体缺项与影响，只询问执行者确实不能自行解决的信息。能完成的模块继续，不将mock验收当真实生成验收。
- 执行软件受上下文/会话时长限制：先保存进度、未完成步骤、日志位置与Git状态。支持持久任务则续跑；否则交付续接指令。文档无法保证第三方软件跨会话永久运行。

## 4. 进度文件结构
PROGRESS.md每模块记录：status（pending/in_progress/verified_local/pushed/blocked），需求ID，代码路径，自检命令与结果，浏览器证据，提交SHA，远端分支，CI状态，未完成项，下一动作。
FEATURE-MATRIX.md每个正式入口记录：功能ID、用户目标、输入、前端入口、API/后端、数据归属、结果、异常恢复、费用、测试证据、完成模块。覆盖首页/登录/商品/素材/信息/推荐/品牌模板/报价额度/任务/作品/编辑/维护/SKU/下载。
DECISIONS.md只记录影响后续行为的决定：原因、备选方案、兼容影响；不要堆叠聊天过程。
reports/Mxx.md记录本模块结果。FINAL-E2E.md记录最终覆盖、环境、版本、模拟与真实证据、失败修复、剩余外部阻塞。

## 5. 最终循环
全部模块推送后，在当前分支最新HEAD运行整体端到端：
1. 新用户首次制作：上传→用途→信息→方案→报价→提交→结果→修改→下载→刷新恢复。
2. 已有商品：沿用信息→新任务→选用版本→恢复旧版→重新下载。
3. 维护：规格变更→受影响图片→选择修改→检查结果→导出；多SKU和补说明图按开放能力全覆盖。
4. 异常：损坏素材、缺关键项、背景默认、额度不足、过期报价、重复提交、网络断开、服务失败、部分成功、下载失败、租户隔离。
5. 文件与账本：实际解码图片、核对尺寸格式/套图清单、任务与扣费关联、重复刷新无重复扣费。
6. 桌面与窄屏：核心页面截图，键盘焦点和错误提示可读。
7. 检查、全量测试、smoke和e2e运行结果记录。真实模型测试须有配置和明确消耗预算；预算未知先完成所有无成本测试，真实部分标待授权预算，不能无限重试扣费。
有问题回对应模块修复，必要回归后提交推送，再重跑受影响的端到端路径。全部必需项通过后提交最终报告与收尾修复，推送并核对远端HEAD；观察最终CI，CI失败继续修复。
最终答复只报告：完成模块、关键行为变化、验证证据、远端分支和SHA、真实限制。Git推送、测试通过、真实模型验收、生产上线分别报告。
