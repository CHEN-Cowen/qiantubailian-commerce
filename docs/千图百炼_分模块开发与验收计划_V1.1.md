## 2. 每个模块的强制工作流程

1. 开始前明确模块范围、依赖、验收标准与分支。只读取/拉取远端不等于提交授权；任何 pull/merge/rebase 前检查工作区，禁止覆盖本地修改。
2. 在用户已授权的当前模块内开发；记录变更、重要决策和未决事项。
3. 完成后执行代码自审与适合该模块的测试，失败则修复并复测。没有通过检查不得宣称自检完成，不得请求将不完整内容作为通过版本提交。
4. 向用户展示具体改动、测试命令与结果、已知限制及提交范围，询问：“本模块自检通过，是否允许同步远端、提交并推送本模块代码？”
5. 只有用户明确授权后才执行该模块 commit 与 push。授权前不创建提交、不推分支、不发 PR；不同模块不自动沿用上一模块的提交授权。
6. 提交前检查远端新提交与冲突。如有冲突先处理、复查并运行受影响测试；提交后核对远端 SHA 与本地一致，再报告提交号、分支与仓库链接。
7. 提交推送成功后，单独询问是否开始下一模块。用户允许提交不等于允许下一模块开发。
8. 下一模块未获确认时停止开发，只保留记录与答疑。用户要求调整范围时更新计划再实施。

原则上一个模块一次可评审提交；若确需拆分或补修，先说明具体范围并取得相应授权。禁止自动合并到其他分支、强推、跳过钩子或把凭据写入仓库。

用户原话要点：“每次开发完以后……先需要进行一遍自检”“获得授权后……提交并推送远端”“然后再来询问是否进行下一模块”“所有的任务开发都完成……整体的端到端的自检”。

## 3. 模块划分与实施顺序

模块按依赖串行推进；每个模块内部可并行处理实现与测试，但不可跨越下一模块授权关口。P0—P3 是产品阶段，M01—M12 是可独立审查的开发模块，两套编号不互相替代。

| 模块 | 阶段 | 范围与主要交付 | 核心自检 / 出口 |
|---|---|---|---|
| M01 工程与运行底座 | P0 | 普通工作副本、项目结构、启动配置、最小服务与健康检查、环境变量示例、测试入口、敏感文件忽略规则；核验并冻结技术栈 | 可重复安装启动；无密钥入库；基础测试与启动冒烟通过；远端明确指向私有仓库 |
| M02 商业化 UI 骨架 | P0 | 快捷首页、商品工作台、素材详情、专业抽屉；应用蓝紫云白规范；用显式标记的 mock 数据演示完整首包流程 | 路由/布局/键盘/空态/错误态与移动收折；未上线视频批量入口清楚标记；原型走查 |
| M03 项目、素材与商品事实 | P1 | Project/SourceAsset/ProductTruth 数据及接口、上传与校验、参考职责、事实确认、版本与来源、首期身份与租户归属 | 非法文件、缺图、冲突、关键项未确认拦截；跨租户拒绝；事实新版本不覆盖旧版 |
| M04 模板、品牌、平台与任务快照 | P1 | 模板、品牌基础套件、带来源和有效期的平台规则、交付清单、CommerceSpec 冻结与输入校验 | 规则冲突/过期/缺失可见；旧任务不受新配置覆盖；无依据功效不自动补全 |
| M05 额度账本与任务执行骨架 | P1 | 测试额度、报价/预算预留、幂等、异步队列、任务及尝试状态、取消/超时/恢复、API/SSE；先用确定性模拟 Provider | 并发额度不超卖；重复提交/回调不重复扣费；断线续传；取消后迟到结果不复活；异常恢复 |
| M06 真实生成与商品主体保护 | P1 | Provider Adapter、接现有 Seedream、实际能力校验、主体掩码/合成、参考图职责、生成记录与受控外部调用 | 接口模拟测试与小样真实验证分开；不支持保护时明确拒绝；文件实际格式正确；成本与版本留存 |
| M07 Commerce QA 与人工复核 | P1 | 文件/尺寸/OCR/商品/颜色/视觉检查、证据与区域、硬门槛、未知状态、可裁决项与审核记录 | 已知缺陷阻断；OCR不可读和服务失败待复核；高美学分不能覆盖硬失败；无法用占位检测器放行 |
| M08 自动修订、版本与正式导出 | P1 | 保留正确项、最小改动、轮数/预算/无改善停止、版本对比回退、失效复检、ZIP/manifest、部分包；接通全流程 | 先前通过项不退化；最多轮数/预算可验证；stale不可正式导出；完整包与部分包区分；P1 E2E |

| M12 结果回流、商业化收口与全量验收 | P3 | 采用/驳回反馈、授权效果导入、指标与实验口径、套餐/真实支付退款（条件具备时）、可观测与部署准备；最后全产品E2E | 全链路/权限/账本/故障/回归/成本报告；缺依赖明确阻断；满足最终完成标准 |

M10 涉及两个子域，执行前如实际改动过大，可经用户同意拆为“详情页”和“视频”两个独立模块，每个均执行同样授权流程。M12 中真实支付、外部平台数据和品牌训练不能用模拟实现冒充生产完成。

## 4. 阶段性可用版本

### P0：M01—M02

交付可运行的工程和 A 组合原型。商品事实/QA/费用状态为显式演示数据，不暗示真实生图和真实质检。用户访谈与100 SKU素材招募从P0开始，基准采集持续到M09。

### P1：M03—M09

M03—M05 形成可持久化且预算安全的任务骨架；M06—M08接真实生成、质检、修订及导出，形成首个可试用图片闭环；M09完成候选模型准入与量化评估。M08结束先做一次P1端到端回归，M09再补真实基准验证。

P1只承诺单SKU图片，不将P2视频详情页列为已可用权益。默认首包建议1主图+2卖点图+2场景图，待模板评审冻结。

### P2：M10

详情页先做结构化模块，视频从已通过商品首帧和低幅度运动开始。支持的时长、掩码、多参考与输出格式按供应商实际能力冻结。

### P3：M11—M12

加入多SKU与组织协作，再接结果回流和商业化收口。私有训练属于单独立项评估，除非用户另行授权并提供素材条件，不计入通用SaaS必须训练的交付。

## 5. 自检报告模板

每模块至少给出：

- 范围：模块编号、需求映射、本次完成与未包含内容。
- 改动：主要文件、数据/接口变化、迁移和兼容影响。
- 检查：实际运行命令、通过/失败结果、覆盖的正常与异常情景。
- 依赖：模拟与真实验证分别说明，不能将未运行检查写为通过。
- 风险：剩余阻断、非阻断限制、回退方案。
- 交付：本地可审查结果；然后请求提交推送授权。

无需对每个文案改动编写机械测试；优先验证真实性硬门槛、状态机、并发账本、跨租户、取消和导出资格等真实风险。

## 6. 最终端到端自检清单

全部已授权模块完成后必须执行整体自检，不能只汇总单元测试：

1. 新用户/测试账号进入首页，创建项目、上传真实授权素材、确认事实。
2. 选品牌/模板/平台，检查报价和预算，启动真实或明确隔离的测试供应商任务。
3. 验证排队、生成、SSE断连重连、QA、自动修订、人工复核和版本回退。
4. 注入包装文字错误、主体变形、OCR不可读、规则过期，确认不误标可发布。
5. 验证预算不足、并发预留、重复提交、供应商超时、取消迟到回调、进程恢复和退款释放。
6. 正式合格包与部分包导出，检查文件、尺寸、命名、manifest、来源与质量快照。
7. 覆盖视频异常帧、详情页参数来源、批量独立失败、审批变更失效与反馈口径。
8. 验证跨租户、对象下载、过期签名、管理员/编辑/审核权限与敏感日志。
9. 执行约定规模性能测试、备份恢复演练、模型基准与合格成本核算。
10. 产出最终报告，包含测试环境、命令、案例、实际结果、已知限制、未运行部分和可发布结论。

发现缺陷先修复并重跑受影响链路；最终修复提交仍需用户授权。未具备的外部能力标记“未验收/阻断”，不声称所有功能已完成。上线部署、真实收费和外部发布需各自取得相应授权。

## 7. 当前下一步

**M06 真实生成与商品主体保护**（P1）。开始前必须先读 `outputs/千图百炼_开发交接说明_M06启动包.md`，它是跨窗口、跨软件的唯一权威交接入口，含 M01—M05 的实现契约、M06 范围边界、建议实施顺序与质量红线。

M06 的边界（详见计划第 3 节 M06 行与 PRD 5.3 / 第 8 节 Provider Adapter 契约）：

- Provider Adapter 统一能力：capabilities / validate / estimate / submit / poll / cancel（可选）/ normalize_result；**validate 对不支持的约束必须明确拒绝，禁止静默丢弃主体保护**。
- 商品主体保护：关键包装用真实主体合成、环境由模型生成；原始主体与掩码版本可追溯；掩码外生成、边缘融合、输出压缩后都要检查。
- 接口模拟测试与小样真实验证**分开报告**；不支持保护时明确拒绝；输出文件实际格式正确；成本与版本留存。
- 真实模型接入（如 Seedream / GPT Image）需要用户提供凭据与授权；无凭据时以确定性模拟 Provider 推进，并把「未做真实验证」如实标注，**不得宣称已完成真实生成**。

开始前不创建功能代码、不提交或推送；涉及真实凭据、付费调用或外部发布时另行明确条件。
