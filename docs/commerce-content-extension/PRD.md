# 千图百炼：商品内容维护与补图开发方案

版本：1.0 讨论稿｜日期：2026-10-28｜状态：未实施。

## 1. 摘要与范围

在现有商品图生产能力上增加三个关联模块：商品变更更新助手、SKU 防串图、售前疑问补图。共同目标是让小商家清楚哪些内容已经过时、哪张图属于哪个 SKU，以及应该补哪张说明图。

本方案不是订单、库存、仓储或财务中台。第一版围绕千图百炼内部商品、事实、素材和已制作图片；不承诺自动同步店铺，不把视觉识别当成完整事实核验，也不承诺提升转化或降低退货。

本轮只形成方案，不实施代码，不部署，不自动追加到原绿色体验优化任务。后续开发按本方案的模块执行，并先核对原优化任务的实际完成情况。

## 2. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 产品负责人 | 决定目标商家、允许的内容操作与计费政策 |
| 商家/主理人 | 提供并确认商品事实、SKU、包装内容，选择改图和实际替换状态 |
| 开发 | 落实数据关联、版本、权限、任务、界面和幂等结算 |
| 验收 | 以有证据的样本检查确定错误、未知状态、版本和费用 |
| 内测商家 | 判断是否解决日常维护问题，记录时间与遗漏 |

人员与交付日期暂不指定，以下模块相对顺序不等同工期承诺。

## 3. 背景与目标用户

目标为无专职设计师、经营少量商品与多个规格、需要持续维护商品页面的小商家。需要验证的任务包括包装/规格变动、套装内容调整、多 SKU 图片归属和顾客反复询问。

现有项目已有商品事实、品牌、素材、版本、生产、额度、复核与导出基础；绿色体验优化方案规划了简单制作、单张修改和信息复用。这些能力是否已在当前代码实现，需要开发前核对，不能直接以文档宣称完成。

三个问题：商品变更后漏改旧图；图片与 SKU 或包装内容不一致；顾客疑问反复出现，但没有变成准确的说明图。

## 4. 目标与成功口径

| 目标 | 测量方式 |
| --- | --- |
| 维护少遗漏 | 在预先标注的关联图片样本中，确定依赖应被完整识别；视觉候选单列，不能据未知宣称无遗漏 |
| 不串 SKU | 已知 SKU/数量/规格结构冲突的测试用例全部阻断；对未知视觉判断不宣称全自动准确 |
| 补图有依据 | 每项对外商品陈述都能追到已确认事实或商家提供的有效依据 |
| 少返工 | 记录从发现问题到完成更新的人工操作时间、模型等待、额外修改次数 |
| 持续使用 | 同一商家在第二次真实维护任务中是否再次使用；下载不能代替实际采用 |
| 费用正确 | 重复提交、重试、切版和导出不重复扣费；新生成前报价，费用有明细 |

建议第一轮邀请 5 位商家，每位提供近期真实任务，合计约 10 个案例。可用“人工操作时间较原方法减少 30%”作为试验目标；不是当前成绩，不据小样本推断市场规模和长期效果。

## 5. 用户价值与产品入口

定位：帮助商家保持商品图片准确、及时、一致。

正常制作流程保持简洁。新增能力以商品页和作品页中的“检查与更新”区域呈现，不要求每次生成都走完整维护流程。

入口：

- 商品页：更新商品信息、检查 SKU 图片、根据顾客问题补图。
- 作品页：查看此图使用的信息、所属 SKU、需更新提示。
- 首页：待处理提醒汇总，初期不另外建立复杂一级导航。

每条待办显示原因、受影响对象、证据、下一步操作和费用影响；未知与已确认错误分开。绿色视觉沿用既有方案，警告与错误保留独立状态表达。

## 6. 共用数据与能力

### 6.1 实体关系

复用现有实体，必要时扩展，不创建平行的商品、账户或结算系统。建议业务关系如下，实际表名依当前架构确定：

| 业务对象 | 核心内容 |
| --- | --- |
| 商品 | 商品身份与当前已确认事实版本 |
| SKU/变体 | 所属商品、唯一业务标识、结构化差异、对应确认状态 |
| 包装内容 | 物件名称、数量、单位、包含/不包含、确认来源；与 SKU 版本绑定 |
| 事实条目 | 稳定字段 ID、值、单位、适用商品/SKU、来源、确认状态和版本 |
| 素材 | 所属账户、商品/SKU关联、角色、源文件和版本 |
| 图片版本 | 基于哪些事实/品牌/SKU/素材制作，文字与排版层、选用状态、检查及权益来源 |
| 图片依赖 | 图片版本依赖的字段、素材、Logo、SKU等，关联区域或文字层，以及依赖证据类型 |
| 变更单 | 新旧确认版本、逐字段差异、发起人、影响清单、选择操作及处理结果 |
| 核对问题 | 规则、证据、严重度、候选/确认冲突/待人工/已处理等状态、处理依据 |
| 售前问题组 | 原始脱敏输入、归类、适用 SKU、频次来源、信息缺口、商家确认 |
| 补图任务 | 问题组、图种、事实依据、配置快照、报价、结果与采用反馈 |
| 导出与替换记录 | 实际导出的图片版本、关联渠道标签、人工替换确认；不等同平台发布证明 |

金额、单位、数量须结构化存储；“500ml”与“0.5L”的等价处理使用明确的单位规则，不用模型随意判断。字段稳定身份与文字展示名分离，避免改字段名称导致依赖丢失。

### 6.2 依赖可信度

- **确定依赖**：由本系统编译文字/排版或明确引用素材产生，记录字段和版本，可据此确定受影响。
- **识别候选**：OCR 或视觉模型推测图片包含某信息，仅作为候选，记录置信和来源，不自动等同确定事实。
- **人工关联**：商家对外部图片或历史作品明确关联，记录用户、时间和适用版本。

对没有历史依赖信息的图片不能显示“检查完毕，无需更新”；应标记关联信息不足，允许人工关联。来源追踪不能靠文件名猜测替代。

### 6.3 状态分离

至少分别维护：事实确认、变更处理、图片质量、用户选用、支付权益、外部替换记录。一个维度通过不能自动推导其余维度通过。

变更单：草稿 → 待确认 → 已确认 → 待处理/处理中 → 已完成；可取消，部分失败时保留成功项与未完成项，不能把部分失败显示为整单完成。

“待处理”由关联清单计算。商家可以经说明确认某候选不受影响，但不能把确定事实冲突通过无理由忽略变成合格。

## 7. 功能一：商品变更更新助手

### 7.1 主要流程

1. 商家编辑商品/SKU信息、新包装照片或品牌资料，先保存草稿。
2. 对比当前确认版本，显示变更字段、新旧值、适用范围和来源。提交确认后形成新事实版本及变更单。
3. 建立影响清单：图片版本、受影响字段/素材、旧导出记录、确定依赖或识别候选。
4. 按“只需改文字/排版”“必须换新实拍”“需重生成”“需人工判断”分类。
5. 商家选择操作与范围，看到费用；系统建立独立更新任务并保留旧版。
6. 结果检查和复核通过后选择新版、导出新包；旧图清楚显示基于旧信息。
7. 对旧导出列出替换待办。商家可以人工标记已替换，显示记录者和时间；未接平台 API 时不声称店铺已同步。

### 7.2 变更规则

| 变化 | 推荐动作 | 必须处理的风险 |
| --- | --- | --- |
| 已确认文案/规格文字更新 | 重合成关联文字层，重新检查 | 不能只改某一张而漏掉已知关联图 |
| 包装图更新 | 上传新照片，更新素材来源，重做受影响图 | 不用生成式修改凭空冒充真实新包装 |
| 单件改两件/赠品增减 | 更新包装内容，检查文字和视觉数量 | 不能只把“1”替换成“2”而仍展示一件 |
| Logo/品牌色更新 | 在选择范围内替换图层或重做 | 不暗改历史和运行中的任务 |
| 活动文案到期 | 列出带该活动版本的作品，提示人工确认撤换 | 活动日期等信息来自用户；未接平台不自动下架 |

### 7.3 更新动作与保护

- 提交只绑定该时刻的事实、品牌和来源版本，后续编辑不改变运行中任务。
- 批量操作先展示明细和预算，逐图记录成功/失败；失败可仅重试失败项，成功项不重复计费。
- 旧版本不删除；操作可比较、选用和恢复。恢复旧图不代表旧事实重新有效，需显示过期状态并重新核对导出资格。
- 事实再次变化时重新计算影响，旧变更单不覆盖更新的确认版本。冲突明确提示重新载入。
- 外部扁平图先提供人工标记区域/关系；OCR 是辅助，第一版不承诺任意图片文字无损自动替换。

### 7.4 验收例

“30ml → 50ml”只影响实际引用该规格的图片；使用背景照片但无相关依赖的图不默认重生成。缺少依赖的图进入待核对。

“1件 → 2件”同时触发包装数量与视觉检查；即使文字更新完成，视觉未确认也不能自动整单通过。

## 8. 功能二：SKU 防串图与包装内容核对

### 8.1 SKU 建档

同一商品下记录 SKU、商家确认的差异属性和包装内容。每个 SKU 绑定已确认实拍/资料，可与商品公共素材共享，但引用时明确适用范围。

单规格商品使用简化入口；多规格才展开表格。系统内部 ID 与商家的 SKU 编号区分，不能在多租户间仅按同名 SKU 寻图。

### 8.2 检查分三层

1. **确定关联**：图片、素材、配置和交付指向的 SKU 是否一致；已知不适用图片被选入另一 SKU 时阻断。
2. **结构化内容**：文字层中的数量、尺寸、单位、规格与确认档案是否冲突；包装包含物是否遗漏或前后矛盾。
3. **视觉候选**：图中颜色、物件数量、配件、包装等是否疑似不符。存在遮挡、反光、同色多物件或比例问题时保留未知，提示人工复核。

检查结果展示原图、当前图、SKU、相关事实和冲突区域，不能只给一个无法解释的风险分数。

### 8.3 处理与交付

确定引用错图时，提供“选择正确图片”“更正真实归属”“重做该图”。更正归属需要核对实拍与事实，不能简单删除关联来解除阻断。

视觉候选允许人工核对并记录理由和依据；已确认的结构冲突必须更正或重新确认真实商品信息。处理范围绑定当前图片/事实版本，不用一次人工确认永久放行后续版本。

导出按商品/SKU分目录和明细命名，记录版本，防止 ZIP 中混入其他规格结果；文件名不是鉴权依据。

组合装须区分“同一物件多个”与“多个不同物件”，允许展示用装饰物标记“不包含”；不得误把背景道具当作随包装交付。

### 8.4 验收例

- 蓝色 SKU 选入明确绑定红色 SKU 的图，确定冲突阻断。
- 单件 SKU 文案写“两件”，确定冲突阻断。
- 图中似有两件但被遮挡，提示未知/人工核对，不生成假的确定结论。
- 全部 SKU 共用 Logo 可以复用；各 SKU 特有包装图不能无确认串用。
- 修复一个 SKU 的图片不改另一个 SKU 的选用版本。

## 9. 功能三：售前疑问补图助手

### 9.1 第一版输入

先支持商家手动输入问题或粘贴脱敏的问题列表；不接客服账号、不抓取店铺、不导入完整聊天记录。提醒移除姓名、电话、地址、订单号等个人数据；后端按长度和格式限制，并对明显个人信息提示处理。

没有真实频次时只显示“输入的问题”，不能伪造“高频/顾客反馈多少次”。商家可以手动填写来源和次数，明确标注人工提供。

### 9.2 从疑问到补图

1. 关联商品/SKU，输入疑问。
2. 提出可编辑的归类：数量/包含物、尺寸、规格差别、使用方式、其他。
3. 匹配当前确认信息与已有图片；先给出“已有图可用”“缺少事实”“建议补图”三类结果。
4. 缺少尺寸等资料时，要求商家提供测量值或依据；无法判断时暂停相应陈述，不推测性能和安全适用性。
5. 推荐一个明确图种与可编辑的内容提纲，预览将出现的文字和依据信息，由商家确认。
6. 先复用已有照片、文字排版与图表；确有必要才调用生成模型，提前报价。
7. 检查、复核、选用和导出进入现有版本流程。记录是否采用、未采用原因与后续问题反馈。

### 9.3 首批图种

| 疑问 | 图种 | 前置事实 |
| --- | --- | --- |
| 收到几个、有哪些配件 | 包装内容清单图 | 物件/数量/单位、包含/不包含及照片 |
| 有多大、能放在哪里 | 尺寸说明图 | 已测量尺寸、单位、测量口径；适配结论另需依据 |
| 两个规格有什么差别 | SKU 对比图 | 已确认差异与各自素材 |

第一版就做上述三种，不同时覆盖所有行业知识。说明图采用可编辑的确定性排版，优先保证文字和对应关系，而不是一律交给模型绘制中文文字。

图片可说明已确认尺寸，但不能仅凭尺寸表就断言“适用于所有抽屉”；使用方法与性能需额外依据。不将模型意见写成商品事实。

### 9.4 后续更新

补图保存所使用的事实/SKU依赖；之后数量、尺寸或包装变化时，自动进入功能一的影响清单。用户再次提出同一问题时先展示现有适用图，避免无意义重复生成。

采用反馈不等于减少询问或提升转化。没有店铺真实数据时，只记录商家反馈，不声称效果已归因。

## 10. 计费、权限与运行要求

### 10.1 建议第一版计费政策

- 查询关联、结构核对、人工标记和查看建议不消耗生图额度；OCR/视觉检测等高成本功能需设置明确预算、限额和并发，不暗中无限调用付费服务。
- 基于已有底图修改文字、制作基础清单/尺寸/对比排版不额外消耗生图额度。高资源场景可以合理限制频率；若以后新增检测套餐另行明确收费，第一版不混在生图点数中暗扣。
- 新调用生图模型的操作，在执行前报价并预留，按新增合格成品结算。失败、取消、待复核沿用既有可解释规则。
- 相同结果和成功项只计费一次；重复提交、批量重试、恢复版本和下载不重复收费。
- 免费编辑和补图不改变源素材的权益；以未付费结果为底图的衍生作品仍受原下载限制。
- 检查出错时用户确认不等于满足成品结算条件；真实收费与支付条件另行验收。

### 10.2 权限与可靠性

- 每个商品、SKU、来源、变更单、问题组、任务和导出都校验当前账户/工作区权限，写入沿用认证与 CSRF。
- 图片内容 URL 亦受鉴权，不能因拥有 ID 即跨账户访问。
- 并发编辑使用版本条件防覆盖；关键操作使用幂等标识。任务和费用关联持久化，可在重启后恢复。
- 对上传、OCR、模型响应、批量规模、文件数量和渲染设置限制与错误反馈。不能把服务异常记录成业务检查通过。
- 审计记录包含操作者、时间、依据版本、实际变动和费用，避免将脱敏前原始聊天或密钥写进日志。
- 保持单实例数据架构的现有边界，不为本轮增设无必要的分布式系统。

## 11. 界面与交互

沿用绿色正式界面方向；正常上新主路径不增加新的强制步骤。

商品详情的“检查与更新”区汇总：待更新作品、SKU 核对项、售前问题。每条待办直接进入对应处理页面。

变更页：旧/新信息对比 → 影响清单 → 动作与预算 → 更新结果 → 替换待办。

SKU 核对页：SKU 选择、确认属性与包含物、对应图片网格、冲突详情、修正操作。移动端使用上下布局。

补图页：问题输入 → 事实缺口与已有图 → 选择建议图种 → 内容确认 → 预览/报价 → 生成与复核。

所有页面必须区分：已确认错误、待人工判断、缺少依据、系统未检查、服务不可用、用户不采用。不能只用红绿颜色表达，也不能让“忽略”按钮变成万能放行。

## 12. 技术拆分与接口契约建议

开发先核对当前实现，扩展领域关系，不根据本文直接机械新增同名表。接口名称可调整，语义须保持：

| 操作 | 输入 | 输出及约束 |
| --- | --- | --- |
| 预览商品变更 | 商品/SKU、基准版本、拟改字段 | 规范化差异、缺少依据、候选影响；不触发生成 |
| 确认变更单 | 预览及基准版本、确认内容、幂等标识 | 新事实版本、变更单、已确认范围；版本冲突拒绝静默覆盖 |
| 查询影响清单 | 变更单/当前版本 | 逐图依赖、证据类型、更新/人工建议与旧导出 |
| 执行选定更新 | 选定项、动作、有效报价、幂等标识 | 持久任务及逐项状态、费用与版本 |
| 保存 SKU 与包含物 | 商品、版本、属性和确认来源 | SKU 版本、校验反馈和影响提示 |
| 发起 SKU 核对 | SKU 与图片版本集合 | 结构冲突和视觉候选分列，服务不可用明确标记 |
| 处理核对问题 | 问题版本、修正或人工理由 | 修正结果或有范围的复核记录，保留审计 |
| 分析售前问题 | 商品/SKU、脱敏问题和可选人工频次 | 归类建议、已有图、事实缺口；不自动补事实 |
| 创建补图方案 | 问题组、图种、确认事实 | 文字/排版提纲、来源快照、预算需求 |
| 执行补图 | 确认方案、报价与幂等标识 | 现有任务/版本/质检/导出流程中的结果 |
| 人工记录外部替换 | 导出记录、渠道标签、确认 | 明确标为用户确认，不伪造平台回执 |

共同验收失败类型：未认证、越权、输入无效、事实未确认、来源版本冲突、报价失效、额度不足、不支持的能力、服务不可用。统一可理解的错误，不向用户暴露敏感栈信息。

## 13. 模块化实施顺序

### M00：基线、依赖与契约

阅读原体验优化接手包，核对当前分支、未提交修改、已有修复、事实与排版层、单张版本及费用基础。列出已实现/缺失/受外部限制的能力；相关阻断问题先修复。明确实体关系、接口和测试样本。

验收：可运行基线、没有覆盖既有用户修改；文档中的历史成绩不冒充当前测试。基础依赖没有完成时先补足，不在两条任务中分别改写同一逻辑。

### M01：商品/SKU/图片依赖与导出关联

实现 SKU 版本、包含物、稳定事实字段、图片版本的确定依赖和来源记录。旧数据迁移为“依赖未知”而不是伪造完整关系；支持人工关联。

验收：新结果可追溯；旧数据可读；跨租户隔离；删除替换素材不静默破坏历史；单位和版本检查正确。

### M02：商品变更更新助手

实现变更预览、确认、影响清单、分类动作、预算、逐图更新、失效提示和替换待办。衔接现有单张修改，不能另起重复生图系统。

验收：文案变更只更新确定依赖图；包装/数量变更需正确证据与视觉核对；部分失败可恢复；旧版本存在；外部替换状态真实。

### M03：SKU 防串图

先完成确定关联与结构化冲突检查，再接可用的视觉候选；实现问题解释、修复、版本化人工复核和按 SKU 导出。

验收：颜色归属、数量、配件和规格结构冲突被识别；未知不冒充通过；批量与导出不会串用其他 SKU 或租户图片。

### M04：售前疑问补图

实现脱敏输入、归类、既有图匹配、事实缺口、三种补图模板、商家确认与任务/权益关联。新图依赖可进入变更助手。

验收：无依据不编造；没有频次不宣称高频；已有适用图优先复用；中文文字与关系正确；用户未采用有记录但不伪造经营收益。

### M05：统一体验、费用与异常恢复

补齐绿色页面、手机端、状态、批量规模限制、并发、重启、失效版本、幂等与源图权益检查。实际开发中这些保护须随模块实现，本模块负责跨模块联调，不能延后基本鉴权到最后。

验收：三个功能使用同一事实与版本，费用一致，重复操作安全，来源/状态可解释。

### M06：端到端验证与交付

执行下节测试并修复。检查内部逻辑、界面及真实服务效果的边界，更新操作说明、截图、限制与实际验证记录。

## 14. 开发、自测、提交与推送约束

若后续获得实施授权，沿用用户已确定流程：每模块开发 → 自测 → 发现问题修复 → 复测通过 → 审查差异 → 独立提交 → 推送并确认远端包含提交 → 自动下一模块，不逐模块等待确认。

全部模块完成后再整体端到端自测；发现问题继续修复和复测，必要整体检查通过后提交推送最终修复和验收记录。即使无代码修复，也提交真实验收文档。测试/推送失败不报告成功，保留成果并解决具体阻碍。

提交只包含明确相关改动，保护已有用户修改；不上传会话、密钥、真实客服记录和未授权素材，不自动合并默认分支或强制覆盖远端。

本方案不直接替代原已授权的开发提示词，也不构成当前立即实施授权。确认排入后再将它作为扩展阶段，防止其他软件在原任务中途擅自扩范围。

## 15. 最终端到端验收场景

1. 建立商品及红/蓝两个 SKU，各自关联真实照片、确认属性和包含物，制作并导出图片。
2. 蓝色 SKU 错选红色专属图，检查阻断；修正后只影响蓝色 SKU。
3. 单件文案写两件，结构冲突阻断；仅视觉疑似两件的遮挡图进入人工核对。
4. 修改已确认规格，已知依赖图完整进入更新清单；缺少依赖的旧图明确待核对。
5. 只改文字，不重新调用生图、不重复扣费、不变其他图片选用版本；重新执行相关检查。
6. 改包装和套装数量，要求新照片/内容依据，不以换字代替实际商品变化。
7. 批量更新一部分失败，成功项保留且只结算一次，重启后只处理未完成项。
8. 事实再次变更或并发编辑，旧客户端不能覆盖新版本；旧导出和待替换记录可追踪。
9. 输入“包含哪些配件”，有事实时生成清单图，无事实时提示补充而不是编造。
10. 输入尺寸疑问，没有测量值不能声称已核实；有依据后生成三种模板之一，文字可编辑。
11. 相同问题已有适用说明图时优先展示；后来事实变更，新说明图能进入影响清单。
12. 免费排版和补图不绕过未付费源图权限；重复点击、重试、导出、切换版本不重复收费。
13. 两个账户互相猜测商品、SKU、任务、图片与导出 ID 均不能越权；认证与写入保护存在。
14. OCR/视觉/生图服务缺失或失败时，确定检查仍可执行，未知或不可用如实显示，不静默通过。
15. 桌面和手机能完成所有核心流程；外部替换仅人工确认，不出现假的平台已发布回执。

对确定规则使用自动回归，界面用真实浏览器走通；图片效果用合法真实样本及授权服务验收。内部模拟与真实外部效果分列，不能用截图或接口返回成功替代内容核验。

## 16. 发布与试点

首版仅开放受控商家内测，保留功能开关和已有制作流程；新增字段兼容旧数据。新增任务与费用数据必须可恢复，出现问题可停止新任务而不删除历史结果。上线前确认备份与恢复方案，不能只验证 UI。

先通过小规模人工试点确认痛点：收集真实变更、SKU误用和顾客问题案例；由产品人员手工做影响清单/核对/补图，确认用户需要后再产品化。用户可明确选择三项全部实施，但不能据此声称需求已经验证。

如果商品变更低频、疑问补图高频，按证据调整后续优先级；M01 的事实与依赖基础仍共用。不要以新功能数量作为项目成功指标。

## 17. 交付物与完成定义

交付：功能代码、必要回归测试、数据兼容说明、接口契约、操作说明、模块执行记录、端到端结果、桌面/手机截图、实际预览入口、费用检查和外部限制。

开发完成需满足：需求映射有证据、确定规则测试通过、三个流程联通、费用与权限无已知阻断缺陷、相关检查通过、模块及最终记录已提交推送并核对远端。真实效果未验收须单列，不宣称平台合规、收益或退货改善已经成立。
